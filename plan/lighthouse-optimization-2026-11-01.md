# Astro 博客 Lighthouse 与图片迁移审计

日期：2026-11-01。当前阶段仅测量、核对和出方案，不实施产品优化。

## 测量范围

- 远程 CI：`41268083167`，源码 `75b1886`，Lighthouse `13.6.0`，GitHub Ubuntu runner。
- 对 `examples/demo` 执行生产构建后，用 Astro preview 提供页面。手机与桌面分别测试：首页、文章、时间线、系列详情、中文首页；每页三次独立 Chrome 冷启动。
- 摘要取 Performance 得分中位的那一次，其他分数和指标来自同一次采样，并保留三次 Performance 的范围。完整 HTML/JSON 在 Actions artifacts。
- **这是主题 demo 基线，不是个人博客的线上分数。** 个人新博客没有部署地址，私有远端仍为空；本轮没有推送个人内容，也没有在本机运行 Lighthouse 或构建。
- Astro preview 不代表最终 CDN 的 HTTPS、HTTP/2/3、压缩、缓存和地理网络条件；缓存/传输相关建议需要上线后重测。没有真实用户 Core Web Vitals 或交互 INP 数据。
- 个人站静态核对来自 `blog-new/dist` 已有产物，首页文件时间为 2026-10-31 14:42:37；它使用固定的主题包，不等同于当前主题 HEAD 的重新构建。

### 实际扣分证据

- **主要瓶颈是主线程执行和首屏阻塞。** 手机 TBT 为 910–1,000 ms；手机文章的 `bootup-time` 将约 953 ms 总 CPU 时间归于 Prism，其中脚本执行约 845 ms。它支持将按页加载/构建时高亮列为首要优化；这不是“删除后必然节省同样 LCP”的保证。
- `render-blocking-insight` 报告手机首屏潜在收益约 1.08–1.20 s，涉及 jQuery、`js/utils.js`、Pace 和 CSS。各资源收益不能简单相加。应先梳理依赖顺序，再 defer/按需加载，保留 Loading 与 ClientRouter 导航。
- 手机未使用 CSS 估算约 40–52 KiB；`global.css` 在预览环境实际传输约 47 KB。首页不使用的阅读模式、目录和 Prism 样式仍处于加载链上。
- **手机时间线最差：55 分、LCP 5.5 s、TBT 1,000 ms。** 当前摘要没有保存 LCP 元素、完整 filmstrip 和布局位移归因，不能把慢加载武断归因于图片或 Loading。实施前先从完整报告查看 LCP 元素与请求时间，再决定首屏图片优先级、可见性或字体策略。CLS 为 0.068，仍低于本方案 0.1 目标。
- 文章与系列详情 Accessibility 均为 92，但具体节点有区别：文章摘要模块 `#abstract-tag` 和按钮的白色文字/紫色背景对比度约 3.52；系列页 `.reward-link-button` 订阅链接的白色文字/绿色背景对比度约 2.36，均低于对应节点所需 4.5。两类页面的版权区 `.post-copyright__author_img` 链接都缺少可访问名称。
- 桌面首页 Accessibility 为 96：分类链接 `.original` 高度仅 20 px，与标题间距也不足，触发 `target-size`。手机布局没有触发此项，不应只测手机就认为全站通过。
- 英文页 SEO 为 92：`More` / `Learn more` 链接文字不明确。应改为具体目的，例如 `Browse categories` / `About the author`，同步维护 i18n；中文首页 SEO 为 100。
- Best practices 均为 100；这仅是这些实验室检查的结果，不代表所有安全、功能和真实网络场景已验证。


## AVIF / WebP 是否移植

**已移植核心链路，并在个人站产物中实际生效；但仍有覆盖缺口。**

| 能力 | 核对结果 |
|---|---|
| 构建时转换 | Astro integration 在 dev/build 准备资产时调用 Sharp；不是访问网页时转换 |
| 输入范围 | 主题资源、站点 static/public、文章同目录资源；处理本地 JPEG/PNG/WebP/AVIF |
| 格式 | WebP 质量 74；AVIF 质量 44、effort 3 |
| 尺寸 | 96、240、480、800、1200、1600 px；小图不放大，原图不足指定尺寸时以原尺寸封顶 |
| 浏览器选择 | `ResponsiveImage.astro` 输出 AVIF `<source>`、WebP `<source>`、`srcset` 和 `sizes`，由浏览器结合容器声明和屏幕像素密度选择 |
| 默认加载 | `loading="lazy"`、`decoding="async"`；首页精选和文章首图单独使用 eager/high |
| 缓存与去重 | 图片内容与编码参数参与 hash；相同内容复用，未变化的编码结果复用本地构建缓存 |
| 原图 | 保留原图；`data-original` 保留灯箱所需地址 |
| 例外 | SVG、GIF、多帧图片及损坏/不支持的输入保留原资源；外部图片不自动下载转换 |

个人站已有产物的直接证据：

- 244 条源图片记录，1,062 条 WebP 尺寸记录、1,062 条 AVIF 尺寸记录；去重后 **2,062 个变体文件**，合计约 **14.8 MB**。这是整个静态站点的文件总量，不是一次访问下载量。
- 清单引用的变体文件均存在。
- 首页 21 个 AVIF source，SkillShare 文章页 9 个，时间线 25 个；均包含 `srcset/sizes`。

尚未完整覆盖：

1. 普通 Markdown `![]()` 只输出 WebP `srcset`，没有 AVIF `<picture>`，也未填入已知的 `width/height`。`subscribe/index.html` 中的二维码可复现此差异。图片 shortcode 和 Astro 图片组件则支持两种格式。
2. 头像、Loading 图、Footer logo、部分友链/关于页面图片仍直接使用 `<img>` 或 CSS 背景。首页 25 个 img 中 4 个仍引用原尺寸本地图且缺少 HTML 尺寸；CSS 可能预留空间，是否造成 CLS 需结合浏览器测量，不能仅凭属性缺失下结论。
3. 旧配置 `extra.other.avif_enable` 仍在默认配置中，但新生成器没有读取它，当前总是生成 AVIF + WebP。开关兼容性需要补齐。
4. Zola 原先 16 px 模糊占位图并未等价移植；当前主要依靠浏览器原生懒加载。这不影响多尺寸选择，但渐进显示体验不同。
5. 部分 `sizes` 使用固定值或 `100vw`，例如时间线 210 px、普通正文 960 px；需要按真实布局和 DPR 检查，存在选择偏大图片的可能。

相关代码：`packages/theme/scripts/responsive-images.ts`、`scripts/astro-assets.ts`、`src/components/ResponsiveImage.astro`、`src/lib/markdown.ts`（后三项相对 `packages/theme`）。

## 优化方案与顺序

### P0：先减少首屏不需要的资源与主线程阻塞

1. 在内容构建时记录页面能力：代码语言集合、数学公式、目录、评论、音乐、二维码等。Layout 根据页面能力加载资源。
2. Prism 仅保留 core 与当前文档需要的语言；无代码页面不加载。优先评估构建时高亮，同时保留复制、代码折叠等轻量交互。
3. KaTeX 仅有公式的页面使用，优先构建时生成公式 HTML，前端按需加载样式/字体。
4. 评论在接近视口或用户展开时加载；音乐、二维码等由交互触发。保留现有功能，不以删除功能换分。
5. 梳理 jQuery、utils、Pace 与主题脚本的同步依赖，再使用 defer、拆分初始化或按需执行；不能直接给所有脚本 async 导致执行顺序错误。用主线程 profile 检查 Prism、摘要模块和动画初始化。
6. 处理 ClientRouter 导航生命周期：首次访问和站内切换都能加载目标页依赖；已加载库复用，监听器可清理，避免多次绑定。

验收：无代码/公式的首页和时间线不请求 Prism/KaTeX；从首页免刷新进入有代码/公式文章后正常显示，复制、目录、评论与语言切换保持可用。

### P1：首屏关键路径与图片覆盖

1. 优先诊断手机时间线的 LCP 元素及显示时机；按完整报告确认的原因修复，不在所有图片上统一 eager/high。随后统一 Markdown、shortcode 和 Astro 组件的图片输出：AVIF/WebP + srcset/sizes + 已知宽高。头像、Loading 图和背景按具体角色补齐。
2. 保留已有首页精选/文章首图的 eager/high，核对其他首屏图的实际优先级；其他图片保持 lazy。调整 `sizes` 为实际卡片/正文宽度，测试 390、1165、1440、1920 px 和 DPR 1/2。
3. 默认 1600 px 上限先保留；只有实测发现大屏首图清晰度不足时，为首图添加 1920/2560 档，不让所有头像和小图都额外编码。
4. 保留用户要求的首次 Loading 和丝滑切换。Loading 在核心页面可用时结束，不等待评论、音乐、统计等非关键服务；避免固定延迟和额外遮挡。需要用 filmstrip/LCP 元素确认它实际影响了什么。
5. 拆分约 270 KB 的 global.css 与页面专属样式；检查重复覆盖规则及首页不使用的 Prism/目录样式。避免为追求少请求合并出更大的全站 CSS。

验收：手机实际选择的 `currentSrc` 与展示尺寸相称；无丢图、无明显布局跳动；图片未加载时预留正确空间；大屏视觉不降级。

### P1：无障碍与基础语义

先修复已测出的节点：摘要模块和订阅按钮的文字对比度、版权作者头像链接名称、桌面分类链接的点击区域，以及英文 More / Learn more 的目的描述。对比度覆盖明暗主题和 hover/focus 状态，名称随语言切换。其他图标按钮、标题层级和 landmarks 可在后续回归中检查，不将其列为本次已经发现的失败。

### P2：构建成本与发布环境

1. 恢复 `avif_enable` 的兼容语义，并明确 widths/quality 配置如何进入缓存 recipe。
2. 在 CI 持久缓存 Sharp 转换结果，按源图/编码参数失效；目前 workflow 主要缓存 npm/Cargo，图片本地缓存不等于跨 runner 缓存。
3. 评估只转换被站点使用的图片，避免对资源目录中未引用图片生成全部尺寸；保留动态配置引用和图片查看器原图，先建立引用清单再做裁剪。
4. 上线后设置压缩及缓存：带 hash 的 `_astro`/`_images` 可长期 immutable；HTML 短缓存或重新验证；未带 hash 的 `/js`、`/dist/css` 必须使用可更新的缓存策略，不能直接一年 immutable。
5. 将此次手动 Lighthouse 流程作为基线。先固定环境与测试内容，稳定后再设置回归阈值，不用 demo 得分承诺个人站线上表现。

## 验收目标（待实施，不是当前实测结果）

- 同一测试环境、同一内容，手机 Performance 中位数目标 ≥90、桌面 ≥95；Accessibility / Best practices / SEO 目标 ≥95，并逐项解释例外。
- LCP 目标 ≤2.5 s、CLS ≤0.1、TBT ≤200 ms；TBT 是实验室指标，不能替代真实 INP。
- 每轮至少三次冷启动，附分数范围和前后对比；保留多语言、免刷新切换、Loading、评论、音乐等原功能的回归检查。
- 个人博客部署后，对真实首页、长文章、图片密集页重新测量，再考虑真实用户监测。

## 执行安排

建议分三轮实施：第一轮处理 Prism/KaTeX 的按页加载、阻塞脚本，并补齐低成本语义问题；第二轮针对时间线 LCP 和图片覆盖，校准 sizes 与宽高；第三轮拆分 CSS、建立图片 CI 缓存，再对个人站部署环境重测。每轮复用本次 5 页 × 2 设备 × 3 次的基线，另做导航与功能回归，保留用户要求的 Loading 和切换体验。

本轮提交的范围只有远程测量 workflow、诊断脚本、分数快照和本文。未实施以上性能优化，未修改个人内容，未进行本地构建或 App 打包。
